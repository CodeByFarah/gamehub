# Security

## Threat model

What this design actually defends against, and what it does not.

| Threat | Defence |
|---|---|
| Credential stuffing | BCrypt cost 12; identical 401 for unknown user and wrong password |
| Account enumeration | Login and registration errors name no field; unknown-user path still hashes |
| Token forgery | HS256 with a key that has no default, validated at startup |
| Refresh token used as access token | Token type is a claim, checked on every verification |
| Privilege escalation via request body | No endpoint accepts a user id; identity comes from the token |
| IDOR | 404 rather than 403 for resources you do not own |
| SQL injection | Parameterised queries throughout; model output never reaches SQL |
| Prompt injection | Architectural containment, not filtering. See below |
| Secret leakage in logs | `toString()` overridden on every type holding one |
| Stack trace disclosure | One handler shapes every exception; traces never returned |
| Resource exhaustion | Payload caps, prompt caps, bounded pools, rate limits |

**Not defended against:** DDoS, unauthenticated endpoint abuse, a stolen
refresh token before the account is suspended, and anything requiring a WAF.
All listed as gaps below rather than papered over.

## Authentication

Two token types, with deliberately opposite properties:

| | Access | Refresh |
|---|---|---|
| Lifetime | 15 minutes | 30 days |
| Revocable | No | Effectively yes |
| Carries roles | Yes | **No** |

Access tokens are not revocable, so the only thing limiting the damage of a
stolen one is how quickly it expires. Refresh tokens are long-lived but the
user record is **re-read on every refresh**, so a suspended account stops
receiving new access tokens even though its refresh token is still
cryptographically valid.

Refresh tokens carry no roles for the same reason: baking roles into a 30-day
token would mean a revoked administrator kept their privileges for a month.

The token type is a claim and is checked on every verification. Without that
check a refresh token would be accepted as an access token, handing an
attacker a 30-day API credential instead of a 15-minute one.

### Why HS256 and not RS256

One service issues and one verifies, so there is no third party needing a
public key. Asymmetric signing buys nothing here and adds key distribution.

This becomes the wrong answer the moment a second service needs to verify
tokens without being able to mint them. Recorded here rather than left as an
assumption.

### Every parse failure looks the same

Expired, bad signature, wrong issuer, wrong type: all return empty. The
distinction is kept in the log, where only we can see it. Reporting it would
tell an attacker which part of a forged token to fix next.

## Passwords

BCrypt cost 12, not the Spring default of 10.

Each increment doubles the work an attacker must do per guess. At 12 a hash
costs roughly a quarter second of CPU: tolerable on a login path, painful at
offline-cracking scale. Higher would start to make login itself a
denial-of-service vector against our own API.

Minimum length 12, with **no composition rules**. Length dominates character
classes for real resistance to guessing, and composition rules push people
towards predictable substitutions. The 128-character upper bound stops a
multi-megabyte password turning BCrypt into a DoS vector.

Tests use cost 4. At 12, a suite registering many users spends minutes on pure
key stretching for no test value.

## Secrets

**Nothing secret is committed.** `.env` and `terraform.tfvars` are
git-ignored; only `.example` files exist, and every value in them is a
placeholder.

`JWT_SECRET` has **no default and no fallback**, with a 32-character minimum
enforced at startup. A development default would inevitably reach production,
and a JWT signing key public in a git history is equivalent to no
authentication at all: anyone can mint a token for any user id. Refusing to
start is the only safe behaviour.

In Cloud Run every secret arrives from Secret Manager as an environment
variable, granted **per secret** rather than project-wide. A `secretAccessor`
role at project scope would let the service read every secret in the project,
including ones belonging to other systems.

The JWT key and database password are generated by Terraform and never written
down by a human. A password chosen by a person ends up in a chat message.

### Redaction

`SecurityProperties`, `AiProperties`, `UserEntity` and `CloudSaveEntity` all
override `toString()`. That override is the only thing standing between a
debug-level log statement, or an exception message that interpolates the
object, and a credential in the log store.

The Gemini key travels in the `x-goog-api-key` **header**, never a query
string. Query strings land in access logs, proxy logs and browser history.

## Authorisation

Default deny:

```java
.anyRequest().authenticated()
```

A new endpoint is protected unless someone deliberately opens it, which is the
correct direction for a mistake to fail in.

`@CurrentUser` exists so no controller reaches into `SecurityContextHolder`
and no endpoint accepts a user id. If the annotation is used on an unprotected
endpoint it **throws** rather than injecting null, because silently handing a
handler an anonymous request it treats as authenticated is the failure mode
worth making loud.

## CSRF

Disabled, and safe **only** because the API is stateless and authenticates
with an `Authorization` header. CSRF attacks rely on the browser attaching an
ambient credential such as a cookie; a header a site cannot set is not
ambient.

If this API ever issues a session cookie, CSRF protection must come back. That
is a real condition, not a formality.

## CORS

`allowedOrigins` is **empty by default**. The Android client does not use CORS
at all, so the permissive wildcard that usually appears here would be pure
attack surface with no consumer.

## Prompt injection

Filtering is a reduction in attack surface, not a guarantee. No input filter
makes an LLM injection-proof, and claiming otherwise is the dangerous part.

The real containment is architectural: **model output is only ever used as
search filters drawn from a fixed vocabulary, or as display text.** It never
becomes SQL, a command, a file path, or an authorisation decision. The worst a
successful injection achieves is a strange search result.

## Input validation

Bean validation at the DTO, business rules in the service, constraints in the
schema. Three layers, and the database one is the one that matters: it is the
last line of defence against any path that bypasses the others.

Rejected values are **never echoed** in a validation error. They may be a
password or a save blob, and they would land in logs and in client-side error
displays alike.

## Actuator exposure

```yaml
include: health,info,prometheus,metrics
```

Only what is needed. `/env` leaks configuration and `/heapdump` leaks memory,
which can contain tokens and passwords in flight.

`show-details: when-authorized` in every deployed profile, `always` only in
`local`. Full health detail tells an attacker which dependencies exist and
whether they are reachable.

## Container and network

- Non-root user in the image.
- Multi-stage build, so no compiler and no source ship to production.
- `ExitOnOutOfMemoryError`: a JVM that has exhausted its heap will not
  recover, and a process answering health checks while failing every request
  is worse than one that dies and gets replaced.
- Cloud SQL and Memorystore have **no public IP**. The only route in is the
  VPC connector.
- A dedicated service account per service, never the Compute Engine default,
  which is shared by everything in the project and carries far broader
  permissions than any one service needs.

## Supply chain

CI runs:

- **Gitleaks over the full history.** A secret added and then amended away is
  still in the history and still leaked, so `fetch-depth: 0` is deliberate.
- **Dependency review**, failing on high severity.
- **Trivy on the built image**, failing on fixable high or critical findings.
  Unfixed findings are reported but do not block, because there is nothing to
  do about them and a permanently red pipeline gets ignored.

## Gaps

- **No refresh-token revocation list.** Tokens carry a `jti` so one could be
  added; today revocation depends on suspending the account.
- **No rate limiting on unauthenticated endpoints.** The limiter keys on the
  authenticated principal, so catalogue browsing is unprotected.
- **No account lockout** after repeated failures.
- **No MFA.**
- **No audit log** of security-relevant events beyond application logs.
- **No penetration testing.** Nothing here has been adversarially tested, and
  no claim in this document should be read as if it had been.
